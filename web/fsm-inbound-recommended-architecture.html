  • 1a PUSH (preferred): S/4HANA Cloud Public Edition sends a standard business event through its built-in Enterprise Event Enablement channel (600+ standard events published on the SAP Business Accelerator Hub) and CPI receives it. Near real time. 1b PULL (backup): CPI checks the existing S/4 APIs on a timer for records changed since the last check — one central check instead of ten FSMs each checking. Chosen per object; both feed step 2 the same way.
  • 2: events carry only the record key — CPI always re-reads the full record from S/4 before sending it out, so what is delivered is always the current state, even if events arrive late or out of order.
  • 3: the subscription list is plain configuration under change control; an FSM physically cannot receive data outside its own contracts (this is where Defence data separation is enforced).
  • 4: one queue per FSM: if one FSM is down, the others keep receiving; messages that keep failing move to that FSM's error queue and its support team is alerted.
  • 7: every receiving system applies the data as insert-or-update ("upsert") on the S/4 record key — receiving the same message twice causes no harm.
  • Works for documents created through the canonical leg too: a service order or purchase order posted into S/4 by an FSM's canonical message (Leg 1) is detected exactly like any other change — detection does not care how the document got into S/4. The fast acknowledgement (status + correlation ID) stays as designed; the document details then come back to the originating FSM as a push carrying the S/4 document number, status and values, matched to its request via the correlation ID. That replaces today's "read the warehouse to see what happened to what I sent" — and every other subscribed FSM gets the same document through its own subscription. No loop risk: FSMs apply the inbound push as a system update; it never re-triggers a canonical send.

SLIDE 8 / 10 — DIRECT DATABASE UPDATE INTO AN FSM (ruled out)

"Why not have CPI write straight into the FSM database?" — because it can't for most, and shouldn't for any

Expected question, answered up front. Writing into an application's database from outside skips the application itself — and for the SaaS FSMs there is no database to reach in the first place.

⚠ Be precise on Friday: CPI CAN technically update a database — that is not the constraint. SAP Integration Suite ships a JDBC receiver adapter that can run INSERT / UPDATE / DELETE and stored procedures against Oracle, MS SQL Server, IBM DB2, PostgreSQL, HANA and others — including on-premise databases via SAP Cloud Connector. So "CPI can't do it" is the wrong argument and will lose the room the moment someone opens the adapter list. The correct argument: capability ≠ recommendation. SAP's own published guidance (the Integration Solution Advisory Methodology and the Clean Core integration white paper) is API-first and event-first; the JDBC adapter exists for legacy and edge cases — typically staging tables or databases you own outright — not for writing into a vendor application's tables. Using it against JAMS's database would be us choosing a pattern SAP documents as the exception, against every reason listed below.
FSMIs direct DB write even possible?
ServiceNow (ITSM / Defence)No. SaaS — ServiceNow does not expose its database to customers at all. Every inbound integration goes through its APIs (Import Set / Table). There is nothing to connect a SQL write to.
SitetrackerNo. SaaS on the Salesforce platform — same situation: platform APIs are the only inbound path.
JAMSTechnically yes — and still the wrong choice (reasons below). Note today's pattern is JAMS reading the Jobpac warehouse; no system writes into JAMS's own database from outside today. Direct write would be a new, tighter coupling introduced in the same program that is retiring the last database-level integration.
  • It skips the application's own logic. Validations, workflow triggers, notifications, calculated fields, security rules and audit history all live in the application layer. A SQL write updates the table but the application never "sees" the change — records can end up in states the application itself could never create, and nobody can tell how they got there.
  • The database schema is not a contract. Vendors change internal tables between versions without notice. Every FSM upgrade becomes a re-test (and possible rewrite) of the integration. An API is a published, versioned contract; a table layout is not.
  • Vendor support is at risk. Writing directly to an application's tables typically voids or complicates support for the affected data — the vendor cannot warrant data their application didn't write.
  • Security and audit get worse, not better. Middleware holding database write credentials is a far larger attack surface than one scoped API user, and contract-level access control plus audit trail exist in the application layer, not in SQL.
  • It is a named industry anti-pattern. Integration through a shared/written-to database is a classic enterprise-integration anti-pattern — "Integration databases: don't do it. Not even with views. Not even with stored procedures." (Michael Nygard, Release It!). It also contradicts the SAP clean-core, API-led direction the program has already adopted.
  • The right answer gives the same outcome safely: the small JAMS upsert endpoint (slide 4) puts the same data in the same JAMS tables — but through JAMS's own logic, with JAMS's own validation and audit. Equal effort to the pull build (Trajce), none of the risks above.
Position for Friday: direct database update is not an option for the fleet (impossible for SaaS FSMs) and not acceptable for JAMS (unsupported, upgrade-fragile, unauditable). It is not a fifth delivery option.
