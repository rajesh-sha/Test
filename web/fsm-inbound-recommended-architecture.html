Getting S/4HANA data to the field systems — final recommended design

Five short sections. Everything deeper is in the appendix at the end. Design Council, Friday.
1 OF 5 — THE DECISION

CPI does the work once. Every field system just receives its own data.

Instead of ten field systems each building schedules, data-fetching and filtering, CPI detects every change once and delivers to each system in the way that system already accepts.

2 OF 5 — HOW IT WORKS

Seven steps — the same for every data set and every system

  1. A record changes in S/4HANA. Created by a field system's own message, typed in by a user, or posted by anything else — it makes no difference.
  2. CPI finds out. S/4 sends a change notice the moment it happens; where no notice exists, CPI asks on a timer "what changed since last time?". (The change notice channel is already switched on and working in our system.)
  3. CPI reads the full record fresh from S/4 — so what goes out is always the current state, never stale.
  4. CPI wraps it in the one standard message, including the tracking reference the sending system can match against what it sent.
  5. CPI checks the subscription list: which systems want this kind of data, for this contract. A system can never receive data outside its own contracts — this is how Defence separation is enforced, in one central place.
  6. CPI delivers it the way each system accepts — a web service call or a file. If a system is down, messages queue and retry automatically; one system being down never delays another; nothing is ever silently lost.
  7. The system saves it itself: create if new, update if existing, matched on the S/4 document number. Receiving the same message twice causes no harm.
This also closes the loop: a work order JAMS sends to S/4 comes back to JAMS automatically with its S/4 document number and status — replacing today's database queries against the Jobpac warehouse.

5 OF 5 — QUESTIONS ALREADY SETTLED

Asked and answered — one line each, detail in the appendix

  • Can it publish everything the field systems need? Yes — all seven kinds of data, using the same S/4 APIs already proven for the fetch design. Nothing new is needed from S/4.
  • Do records created by a field system come back to it? Yes, automatically, with the S/4 document number — matched by the tracking reference it already holds. No loops.
  • Why not write into the field systems' databases? Impossible for the cloud systems (they expose no database), and wrong for JAMS — it would bypass JAMS's own logic and break on upgrades. CPI technically can; SAP's own guidance says don't.
  • Why not let systems subscribe to SAP's event service directly? Events carry only a record ID, can't filter by contract, and can't convert formats — every system would end up rebuilding the work. The event service has exactly one job here: telling CPI something changed.
  • What if something is down or fails? Messages queue per system, retry automatically, alert a named owner if they keep failing, and can be re-sent — including whole date ranges for first loads and recovery.

A3 — Why writing into a field system's database is ruled out
  • ServiceNow and Sitetracker are cloud products that expose no database at all — there is nothing to write to. So it could never be the standard pattern.
  • For JAMS it is technically possible and still wrong: it bypasses JAMS's own checks, workflows and audit history; the internal table layout changes with upgrades and is not a contract; vendors cannot support data their application didn't write.
  • CPI does have a database adapter — capability is not the constraint. SAP's own integration guidance is API-first, with database writing reserved for systems you own outright.
  • The JAMS receiving services put the same data in the same place through JAMS's own logic, at equal effort.
A4 — Why systems can't just subscribe to SAP's event service directly
  • SAP's change notices carry the record's ID only — by design. The receiver is expected to call back for the data. Direct subscription would force every field system to build fetch-and-convert logic — the exact burden this design removes.
  • The event service filters by topic name only; filtering by contract is documented by SAP as an anti-pattern. Defence separation could not be enforced.
  • It does not convert formats — ServiceNow's import interface and Salesforce's save interface need their own shapes, which is CPI's conversion job.
  • A middle variant (CPI publishes finished messages to event topics; the event service delivers by webhook) is viable later for systems that accept the standard message directly — it swaps only the delivery plumbing and needs no rework of the rest.
A5 — Licence evidence (checked in our own accounts)
  • The change-notice framework is part of S/4HANA Cloud — configured in standard apps; the channel is active in our tenant today.
  • The "SAP S/4HANA Cloud Extensibility" plans (api-access, messaging) sit in our global account with Commercial Type: none — included with the S/4 subscription. "Not assigned" just means an administrator hasn't assigned them to a subaccount yet.
  • The event broker (EMIS) is included in the Integration Suite editions at no extra cost — and its active channel proves it is on.
  • Advanced Event Mesh (the separately-priced high-volume product) is not required.
  • No AI service is used anywhere. The one commercial variable: message volume under our existing Integration Suite metering — sizing in progress.
