FSM Canonical Architecture — Inbound & Response

Project Apollo · SAP CPI · Working translation of the build walkthrough, with Shankar’s open points mapped into the design and solutions for sequencing, error handling/DLQ and FSM onboarding · v0.2 — 13 Aug 2026

The architecture in one paragraph. Every field-service system (FSM) — GEMS, ITSM, Mars, Defence, Site Tracker, ODM — reaches S/4HANA through one shared CPI entry. A message arrives either by push (the FSM calls one universal HTTPS endpoint) or by pull (one CPI timer flow per FSM fetches on a schedule). Both hand the payload to a shared system router, which reads the FSM_System header and passes the message to that system’s own mapping flow — the only system-specific build in the chain — where the payload is converted into the agreed canonical structure. Most message types are then dropped onto a JMS queue named after the message type and the FSM gets an immediate acknowledgement; a queue reader picks the message up and runs the FSM-agnostic canonical execution that calls S/4HANA. Material usage runs synchronously (no queue) so the stock answer goes straight back. Responses to the FSM come two ways: a status acknowledgement on the first leg (status + correlation ID, no document details, no PATCH back into the FSM), and a GET-only pull proxy the FSM calls on its own schedule, keyed by contract ID, to fetch S/4 results.

Sources: CPI Inbound diagram · FSM canonical request/response end-to-end diagram · build walkthrough with Thauriq Jappie, 4 Aug 2026 · Shankar Raju’s open-points email, 10 Aug 2026.

1First leg — how a message gets in

One entry for everybody; the only per-system build is the mapping flow at the end.

Shared1A · Push triggerOne universal HTTPS endpoint, all FSM, all scenarios. Accepts payload as-is (JSON or XML), no logic.
→
Shared2 · System routerReads FSM_System header; routes to the system’s mapping flow. Unknown system ends cleanly.
→
System-specific3 · FSM mapping flowLooks up contract & pattern, routes by type + pattern to 1 of 6 mapping steps, builds the canonical payload.
→
AsyncJMS queueQueue name = message type (dynamic). Drop-off returns the async acknowledgement — receipt only.
→
Shared4 · Queue readerPassthrough consumer; hands the canonical payload to execution.
→
Shared5 · Canonical executionFSM-agnostic logic; sequenced S/4HANA API calls per canonical (service order, procurement, material usage, RCTI…).

Material usage (stock consumption / stock confirmation) skips the queue: it is called sync via process direct so the stock answer returns to the caller in the same exchange. Canonicals can also call each other directly (e.g. procurement → material usage) without going back through a queue.

Push (1A)

  • Built once, reused by every FSM. Onboarding a new system needs no change here — hand over the URL and credentials only.
  • Auth is layered: BTP process-integration-runtime instance issues client ID / secret with the ESB messaging.send role; OAuth 2.0 client-credentials (CPI performs the token exchange even if the caller sends basic auth). API Management can be added later to enforce the method.

Pull (1B)

  • One pull flow per FSM system (ITSM first), holding all of that system’s schedules in one place — e.g. work orders every 4 hours, payments weekly. Pull flows call the same system router as push.
  • Pull flows are named for the system they poll (renamed from generic “FSM” labels — agreed on the call).

Routing and the per-system switch

  • The router checks FSM_System: GEMS → GEMS mapping, ITSM → ITSM mapping; anything unconfigured falls to the default route and ends successfully without processing — nothing enters a queue.
  • Two control levers per system without a code change: an externalised configuration parameter that dead-ends a system’s route (channel off), and revoking the system’s service key (no authorisation to call at all).
  • Adding an FSM is a one-time, two-step router change: add the route condition and its process-direct target. Change risk to other systems is minimal because each system’s logic lives in its own mapping flow.

2Mapping flows and queues

Systems conform to the canonical before it — the canonical never adapts to a system.

  • Each FSM’s mapping flow is the only system-specific component. It maps the source payload into the canonical structure so canonical execution can treat every message identically. New FSM = copy an existing mapping flow, adjust the mapping, onboard.
  • Inside the mapping flow: contract + pattern lookup from the shared datastore, then routing by message type + pattern into one of six mapping branches. A splitter runs before the JMS drop, so a multi-type payload is already catered for even though today one payload = one message type.
  • Three target types leaving the mapping flow: JMS drop (most types — queue name derived from message type), direct sync call (material usage: stock consumption, and stock confirmation for pattern 2.2), and the async acknowledgement back to the caller.
  • Queues today are named purely by message type (e.g. PROJECT_WBS, RCTI) — see open point 4 for the proposed standard.

3Second leg — canonical execution

FSM-agnostic; the same logic no matter which system sent the message.

  • The JMS queue reader is a passthrough: it consumes from the queue and hands the canonical payload to the execution flow for that canonical (service order, procurement, material usage, RCTI, etc.).
  • Execution makes the sequenced S/4HANA API calls the canonical requires and logs errors to the canonical error-logging flow.
  • Canonicals can invoke each other by process direct (no queue hop), which is why execution must be callable independently of the queue.
  • Sync responses (material usage) return through the first leg to the caller; S/4 success/error outcomes otherwise surface via the acknowledgement callback and the pull services below.

4Responses back to the FSM

Two pathways — a status callback on the first leg, and a pull endpoint the FSM calls when it wants the data.

Response type 1 — acknowledgement and outcome callback

  • Carries status + correlation ID only — no document details. Document data waits for the pull.
  • No PATCH back into the FSM. The custom ITSM patch (CPI updating ITSM’s records after queueing) was dropped to stay on the standard design; ITSM receives the acknowledgement and does its own update, then fetches results via the pull services. Agreed with Will / ITSM.
  • Nothing is written into FSM records from CPI on either pathway.

Response type 2 — pull of S/4HANA data (CPI proxy)

  • One CPI proxy flow exposes what looks like separate endpoints per object: a wildcard path segment maps the friendly name (e.g. /serviceorder, /journalentry) to the real S/4 OData service or custom CDS view. Consumers see plain HTTPS; CPI speaks OData to S/4.
  • Available today: Service Orders, Enterprise Project List, Customer Invoice, Project Time & Equipment Usage, Supplier Invoice / RCTI Payments, Available Stock Query (plus journal entry built ahead of need). Adding a service is a mapping entry, not a new flow.
  • Hardening enforced in the proxy: GET only; OAuth 2.0 role-based auth; contract ID mandatory, validated against the contracts table persisted in CPI, and injected as a filter so a caller only receives its own contract’s data. Consumers may add further filters (date, job number, field selection).
  • The pull is keyed by contract ID + FSM job number — one address, a registered query per system. One contract ≈ one system; a system with several divisions holds a contract ID per division.

5Traceability and the support model

A single pushed message is at least five iFlow instances in the monitor — support must be able to find all of them from business data.

  • Minimum footprint per pushed message: push trigger → router → system mapping → queue reader → canonical execution = 5 instances, more when canonicals chain. Three messages from three systems = 15+ entries; support cannot work from counts alone.
  • Correlation ID links every instance of one message end to end and is returned to the sender in the response body.
  • Business-data search: every flow is to stamp contract ID and FSM job number (plus correlation ID) as custom header properties, uppercase, consistent spelling — so support can search by the thing the ticket actually quotes (“where is my job 12345”), not by technical IDs. Thauriq to enforce across the team on every integration.
  • These are the same two fields the outbound pull relies on, so support learns one pair of fields for both directions.
  • Open design intent: where flows cannot be reduced, concentrate business logic away from the passthrough legs so support learns quickly that instances 1–2 are plumbing and the mapping + canonical instances are where failures live.

6Shankar’s open points — folded into the architecture

The seven items from Shankar Raju’s email of 10 Aug 2026, each placed where it belongs in the design, with the current position and what remains with Deloitte.

1

Response handling and standard response model

Partially addressed
Where it sits
End of first leg (acknowledgement) + canonical outcome callback + pull proxy (§4).
Position
Two response pathways are designed and building: status + correlation ID acknowledgement (no document details, no PATCH into the FSM) and the contract-keyed pull. Every response body is to carry correlation ID, contract ID and FSM job number as standard fields.
Open with Deloitte
Publish the formal standard response model (structure, status codes, error payload) so every canonical returns the same shape — documented, not tribal.
2

Message ordering and sequencing considerations

Solution proposed
Where it sits
JMS queues between the legs (§2) and the sequenced S/4 calls inside canonical execution (§3).
Position
One payload = one message type, queues are per message type, and execution sequences its own S/4 API calls — but nothing in the base design guarantees cross-message order (e.g. create before change on the same work order) across queue redeliveries and retries.
Solution
Dinesh Balachandran’s payload-selection design (12 Aug) — single-threaded latest-per-key selection before the canonical, non-overlapping batches. See §8.
Open with Deloitte
Adopt the design; validate batch latency and selection cost in SIT; decide one shared canonical queue vs a queue per FSM.
3

Technical and business error handling

Solution proposed
Where it sits
Exception subprocess referenced from the router and every leg; canonical error-logging flow (§3).
Position
A shared exception flow (ServiceNow ticket + email) is being built and will be called from all flows; process-direct failures already bubble up to the calling flow. Business errors from S/4 surface through the outcome callback and pull.
Solution
Smart JMS retry with exception-based routing: business errors return to the FSM via ack/pull (no retry); technical errors retry with backoff, then dead-letter with a ServiceNow ticket + email. See §9.
Open with Deloitte
Confirm retry count + backoff per entity; wire the shared exception flow into the flows already built.
4

Standardisation of queue names

Open
Where it sits
Dynamic JMS drop in every mapping flow (§2).
Position
Queue name = message type today (PROJECT_WBS, RCTI). Proposed standard: [Environment]_[Flow]_[BusinessEntity]_[QueueType], which enables smart JMS retry and exception-based routing and gives DLQs a natural home.
Open with Deloitte
Adopt the structured format from the start — queue renames after go-live are painful. Because the queue name is derived in one place (the dynamic property), the change is cheap now.
5

XSD schemas

Open
Where it sits
The canonical contract at the boundary of every mapping flow (§2) — systems must conform before entry.
Position
Canonical structures exist and are enforced in the mapping flows, but the XSDs have been requested since 24 Jul (again 31 Jul and 4 Aug) and are still not shared, nor the CPI package that holds them.
Open with Deloitte
Publish an XSD per canonical plus the owning package, so new FSM onboarding and our own validation don’t reverse-engineer the structure from iFlows.
6

Naming standard

Partially addressed
Where it sits
All iFlows, endpoints and properties across both legs.
Position
Agreed on the call: system-specific flows are renamed for the system they serve (e.g. the ITSM pull, no longer generic “FSM”), and searchable properties are standardised uppercase with consistent spelling (a contract/contact typo already cost us a search). The Technical Development Standards and Naming Conventions v0.1 document is the reference.
Evidence
The FSM package (21 artifacts) mixes separators and casing (FSM PUSH iFLOW vs FSM_Canonical_Mapping_Router), still holds FSM_Canonical_Mapping_Router_copy, ITSM_TEST and FSM_TEMP_DIRECT_SO, and ContractsCreateUpdate is missing its FSM_ prefix.
Open with Deloitte
Confirm all current iFlows follow the standards document and hold the convention from the beginning — renames get harder with every flow added. See the as-built names in §10.
7

Dead Letter Queue (DLQ)

Solution proposed
Where it sits
After the JMS queues (§2) — the landing place for messages that exhaust retries.
Position
Not in the current build: a message that fails repeatedly today just sits failed in the monitor. Depends on point 4 — the [QueueType] segment of the proposed naming gives DLQs their structure.
Solution
DLQ per business entity paired by the [QueueType] suffix (…_MAIN / …_DLQ), exception-based routing on retry exhaustion, replay keyed on the correlation / contract / job-number headers. See §9.
Open with Deloitte
Confirm DLQ retention, who is authorised to replay, and the reprocessing runbook.

Raised and parked

  • Server-side filter limits on the pull proxy. Consumers can omit date filters and drag a year of data (business partner queries already time out).   • Contract-ID-keyed access. Contract IDs are widely known internally; any system holding a valid OAuth key could query another system’s contract. Per-system technical users would mean a proxy per system (CPI cannot make credentials dynamic — security risk). For legacy systems that can only handle files or table queries, an extra CPI leg on top of the pull proxy (e.g. file drop from the registered query) is the fallback — scope and ownership (Service Stream vs Deloitte) to be agreed case by case.

8Message sequencing — proposed design

Answers open point 2 · proposal by Dinesh Balachandran (GBIS), 12 Aug 2026 · the latest payload per key is selected before the canonical runs.

FSMPayload carries a key (e.g. job number) + timestamp
→
Querying iFlowPull process / API endpoint — existing first leg
→
Selection data storeRaw payloads land here per batch
→
Single-threadedPayload selection iFlowSort key + timestamp desc; keep the latest per key, discard older
→
Canonical queueNo duplicate keys — one latest payload per key
→
Canonical iFlowMulti-threaded execution, safe — keys are unique
→
S/4HANA CloudSequenced API calls per canonical

The fix in one line: if the same job arrives twice in a batch, only the newest payload reaches the canonical — last-write-wins replaces in-flight ordering.

Pre-conditions for the design to hold

  • Payloads are point-in-time snapshots — the latest timestamp already contains every earlier update, so discarding older payloads loses nothing.
  • The payload selection iFlow runs single-threaded — exactly one process performs the de-duplication per batch.
  • Batches never overlap — the next batch starts only when every transaction of the previous batch is terminal (success or failure, retries concluded): the canonical queue is logically empty for that FSM.

Discussion points (12 Aug thread)

  • Throughput (Frank): waiting for the queue to drain before the next batch adds latency — quantify per-batch wait in SIT before committing.
  • Selection cost (Dinesh): expected negligible — no external calls; read the data store, sort by key + timestamp descending, take the first record per key.
  • Design choice: one shared canonical queue vs a queue per FSM — it changes what “empty before the next batch” means and how batches interleave across systems.

9Error handling & DLQ — smart JMS retry design

Answers open points 3 and 7 · pattern per the SAP Community blog Shankar referenced (Smart JMS Retry with Exception-Based Routing) · builds on the queue naming standard from point 4.

MAIN queue[Env]_[Flow]_[Entity]_MAIN — canonical payloads land here
→
Canonical iFlowProcesses the payload; sequenced S/4 API calls
→
ClassifierError classifierException subprocess splits technical vs business on the error type
→
Technical onlySmart retryJMS redelivery count checked; max N with backoff per entity
→
ParkedDLQ[Env]_[Flow]_[Entity]_DLQ — poisoned message, all headers intact
→
Exception flowServiceNow ticket + email carrying correlation ID, contract ID, FSM job number
→
ReprocessSupport fixes cause, replays from DLQ back to MAIN — no payload lost

Business errors never enter this path: an S/4 rejection (bad data, validation) is a final outcome — returned to the FSM via the acknowledgement / pull, no retry, no DLQ. Only technical failures (connectivity, timeout, mapping) retry and dead-letter.

Design rules

  • Retry on the JMS redelivery count (SAPJMSRetries) with backoff — max attempts set per business entity, not one global number.
  • On exhaustion, exception-based routing moves the message to the paired DLQ — the [QueueType] suffix from the naming standard makes every MAIN/DLQ pair self-describing.
  • The DLQ message keeps correlation ID, contract ID and FSM job number headers — the ServiceNow ticket and the parked message always find each other.
  • One shared exception flow, called by every leg via process direct — one place to change ticketing and alerting.

To confirm with Deloitte

  • Retry count + backoff per entity; DLQ retention period; who is authorised to replay.
  • Wiring the shared exception flow into the flows already built.
